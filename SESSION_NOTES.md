# Session Notes — 2026-07-11 / 2026-07-12

## 1. What today's 4 commits contain

**`c5b823ba` — Fix hosted funnel leads pipeline and clean up /f/[id] landing pages**
- `Lead.sourceType` enum was missing `"facebook_funnel"` — the exact value `funnel-submit.ts` writes on every hosted-funnel submission — so every lead from `/f/[id]` silently failed validation and returned a 500. Every hosted-funnel lead, ever, had been lost.
- Surfaced Meta OAuth callback `?meta=error`/`?meta=connected` as a toast on `/facebook-leads` instead of silently dropping the query params.
- Removed the hero image from hosted funnel pages (a stale, low-resolution screenshot asset) in favor of a clean text-only lead-type title header, sourced from a new per-template `displayName` field on all 9 funnel templates.
- Hosted funnel pages now render campaign-specific `benefitBullets` on step 1 (falling back to the template's generic reassurance copy when a campaign has none), use `ctaStrip` for the submit button label, and always append the veteran-targeted templates' government-endorsement disclaimer alongside the bullets (additive, not either/or).
- Bumped `generate-ad-images.ts`'s requested image size to 1536x1024 — turned out to be dead code with zero callers (see follow-ups).

**`6b53e30c` — Ad tracking trust overhaul**
- `syncAdInsights.ts` was overwriting `totalSpend`/`totalLeads`/`totalClicks`/`totalImpressions`/`cpl`/`cpm`/`cpc`/`ctr` with just the current sync's window (7 or 30 days) instead of lifetime totals — every sync silently truncated a campaign's real history. Now recomputed from the full `AdMetricsDaily` history on every sync, with a shrink-guard that warns instead of silently reducing a stored total. Added `windowSpend7d`/`windowLeads7d` as separate fields so window and lifetime numbers can never collide again.
- The scheduled auto-optimize cron (every 6h) has been 403'ing on every single run since it unconditionally required an admin session even after the `CRON_SECRET` check had already passed — meaning the automated ad-optimization/alerting/"replace this ad" email system had never actually executed unattended. Fixed to skip the session check for authenticated cron requests.
- In the same change: deleted `getOutcomeMetrics`/`calculateLeadQualityScore`/`calculatePerformanceScore` in `auto-optimize.ts` — they read `campaign.leadOutcomeStats`/`outcomeStats`, fields nothing in the codebase ever writes, so they always computed zero and were silently overwriting the correct numbers `scoreAdPerformance.ts` had just calculated. `scoreAdPerformance.ts` is now the single source of truth for appointments/sales/costPerAppointment/costPerSale/performanceScore.
- New `lib/facebook/verdictGate.ts` (`hasEnoughData`: 5+ leads, $50+ spend, 72+ hours) applied to `scoreAdPerformance`'s new `LEARNING` class, `recommendations.ts`, `optimizationAlerts.ts` (both winner and loser), and the replace-ad/new-ad email decision — no performance verdict fires on a sample size too small to mean anything.
- `detectCreativeFatigue`/`cplSpikeFlag` compared current CPL/CTR against `previousAvgCpl`/`avgCtr`/`weeklyLeads` fields that are never written anywhere, so 3 of the 4 fatigue signals were mathematically always false (self-referential fallback chains). Replaced with a real current-7-days-vs-prior-7-days trend computed from `AdMetricsDaily`.
- ROAS was computed two different ways in two different dashboards — one used real agent-entered commission revenue, the other (`stats.ts`) queried a field that doesn't exist on the underlying models (always returned 0) and separately summed a flat per-lead-type revenue *estimate*. Unified everywhere on real revenue (`FBLeadCampaign.totalGrossRevenue`); added per-campaign ROAS to the attribution rollups and command-center.
- Server-side premium enforcement: a Facebook-attributed lead can no longer be marked Sold without a recorded premium unless explicitly flagged `premiumPending`. Pending sales are excluded from sales counts/close-rate/cost-per-sale/ROAS until `record-sale.ts` resolves them. Added `Lead.revenuePending`, a "Sold — premium pending" option in `SaleModal`, wired through the 3 disposition UI paths known at the time.
- `trackCRMOutcome.ts`'s silent attribution-loss returns (a sale with no `FBLeadEntry`, a missing `campaignId`, a deleted campaign) now log a structured warning so lost sales are findable, without throwing or surfacing anything to the agent.
- Verified via simulation at every step (32+ checks) plus a full funnel/OTP/lead-pipeline regression suite. `npx tsc --noEmit` clean throughout.

**`ebdf1b5d` — Fix Sold disposition error handling on remaining caller pages**

## 3. Known follow-ups (not fixed this session, intentionally out of scope or lower priority)

- **Harden the auto-optimize per-campaign loop before scale.** It's a plain sequential loop with no per-iteration try/catch and no concurrency limit; a single transient DB error on one campaign aborts the whole run and skips every campaign after it. `scoreAdPerformance` now does ~6 DB round trips per campaign inside this loop (previously zero — it was pure in-memory math), so at hundreds of campaigns this could exceed serverless timeouts. Not an issue at today's scale (13 campaigns), but should be addressed with per-campaign try/catch-and-continue plus batching/a `maxDuration` config before the platform has meaningfully more automation-enabled campaigns.
- **`dial-session.tsx`'s disposition fallback can swallow a rejection.** `persistDisposition` tries `/api/leads/set-disposition` first and silently falls through to a second, weaker candidate (`/api/leads/update`, which doesn't actually apply a status/folder change for this payload shape) on any failure. In the rare case a "Sold" disposition gets rejected here, the agent would see a false "Saved: Sold" toast even though the lead didn't move. Not touched this session — it's a pre-existing pattern used for every disposition type, not something introduced now, and fixing it means touching shared call-session logic beyond this session's scope.
- **Per-ad winner/loser alerts (`optimizationAlerts.ts`) are still CPL-only.** There is no ad-level sales/appointment data anywhere in the system today — `CRMOutcome` is keyed by `(campaignId, userId, date)` with no `metaAdId` dimension, even though the raw event data (`LeadOutcomeEvent`) already carries `metaAdId`/`metaAdsetId` per event. Fixing this properly means either adding `metaAdId` to `CRMOutcome`/`AdMetricsDaily` or aggregating `LeadOutcomeEvent` directly — explicitly out of scope for this batch, but it's the prerequisite for ever making the per-ad "this ad is winning/losing" verdict honest about sales quality, not just lead cost.
- **The cross-account benchmark is unbuilt.** `recommendations.ts` has `bestByLeadType`/`fatiguedByLeadType` maps and `globalWinner` lookup logic already written, referencing hook/creative pattern data — but nothing ever populates those maps (`.set()` is never called), so every "compared to a globally stronger pattern" message silently falls through to a generic fallback. The underlying cross-account data exists (`lib/facebook/globalIntelligence/recomputeGlobalPatterns.ts`, already cron'd every 6h) — it just isn't wired into this specific decision point. Also explicitly out of scope for this batch.
- **Delete the dead `generate-ad-images.ts` endpoint.** Confirmed via repo-wide grep this session — zero callers anywhere. The real hero/creative-image pipeline is a client-side CSS/DOM screenshot (`html-to-image`'s `toPng()` on `ProductionFeedCreative`, captured in `AdWizard.tsx` and posted to `publish-ad.ts` as `renderedCreativeDataUrl`), not an OpenAI call. This file (and its now-unused 1536x1024 size bump from commit 1) can be safely removed.
- **Rotate the old OpenAI API key.** During the same investigation, an attempt to call OpenAI's image API with the key in `.env`/`.env.local` returned `401 Incorrect API key provided`. Since the real pipeline doesn't use OpenAI for images at all, this key may be stale/revoked from an old integration — worth rotating or removing if it's not used elsewhere, since a dead credential sitting in the environment is worth cleaning up regardless.
